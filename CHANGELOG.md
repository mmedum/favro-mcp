## [Unreleased]

### Added (Phase 4 — NL workflow read layer)
- `internal/server`: `Resolver` struct holds a `*favro.Client` plus seven per-resource `cache.TTL[…]` caches (tags, users, collections, widgets, columns, custom fields, groups). Constructed once per `mcp.Server` so cache state is process-wide. Cache TTLs follow plan §7 (5 minutes for slow-changing org metadata: tags, users, custom fields, groups; 60 seconds for collection-scoped lists: collections, widgets, columns).
- `internal/server`: generic `listAllCached[T]` helper centralises the cache-lookup + paginated fetch + cache-write protocol so each resolver method is a 3-line delegation. Reuses `favro.Paginate` for the page walk.
- `internal/server`: `Resolver.Resolve{Tag,User,Collection,Widget,Column,CustomField,Group}(ctx, name, ..., limit, forceRefresh)` return ranked candidates. Score scale: exact match 1.0, prefix 0.7, substring 0.4, no match filtered. Tie-break by name ascending so ordering is deterministic. `limit <= 0` defaults to 10; `limit > 50` is capped at 50 per plan §6a.
- `internal/server`: `Resolver.ResolveUser` matches against the **better of name and email** so an LLM asking for "alice" or "alice@example" both work; email is included in `ResolvedUser` for disambiguation.
- `internal/server`: `Resolver.ResolveWidget` accepts an optional `collectionID` filter applied client-side (avoids a per-collection cache key with redundant data); `ResolvedWidget` includes `Type` and `CollectionIDs` so multiple "Sprint Board" widgets in different collections are distinguishable.
- `internal/server`: `Resolver.ResolveColumn` requires `widgetCommonID` — column names ("Doing", "Done") repeat across widgets and an unscoped resolver would always return ambiguous garbage. Returns `errMissingResolveWidgetCommonID` (typed sentinel) on empty input. Cache is keyed per-widget.
- `internal/server`: `Resolver.ResolveCustomField` includes the field `Type` ("Single select", "Date", etc.) in `ResolvedCustomField` so an LLM can disambiguate between multiple "Priority" fields of different kinds.
- `internal/server`: per-resource `invalidate{Tag,User,Collection,Widget,Column,CustomField,Group}Cache()` package-private hooks for Phase 6 mutating tools to call after successful create / update / delete.
- MCP tools: `favro_resolve_{tag,user,collection,widget,column,custom_field,group}`. All return a candidate list (possibly empty) plus a `cached: bool` so callers know whether a `force_refresh` follow-up might surface newly-created items. `favro_resolve_column` requires `widget_common_id` at the JSON-schema layer (mirrors the underlying API constraint).
- `internal/server`: `Resolver.SearchCards(ctx, query, scope, scopeID, includeArchived, limit, minScore, forceRefresh)` runs a local full-text search over the cards in scope and returns ranked `SearchedCard` hits with snippet, since Favro has no native FT search. Score components are additive (max ~2.0): name phrase +1.0, name token overlap up to +0.6, body phrase +0.5, body token overlap up to +0.5. Distinct-token hits (a token appearing twice still counts once) so the ranker doesn't bias toward verbose cards. Tie-break by name ascending. Empty query short-circuits to no results without touching Favro.
- `internal/server`: `searchCardCache cache.TTL[scopedCorpus]` on Resolver, where `scopedCorpus` holds the raw card list plus its pre-stripped + pre-lowercased name and body strings as parallel slices. Pre-processing once at fetch time means warm-cache repeat queries against the same scope skip both the markdown sweep (~14 regex passes per card) and the per-card `strings.ToLower` (otherwise run by ranker + snippet ≈ 3× per card per query). Cache key format `search:widget:<id>[:+archived]` / `search:collection:<id>[:+archived]` so a single `InvalidatePrefix("search:")` (via `invalidateSearchCardCache`) drops every variant. Plan §7's 60-second TTL. Both scopes paginate fully — the scope's natural size bounds the cost. Every fetch sets `descriptionFormat=markdown` so the markdown stripper sees the format it expects.
- `internal/server`: `stripMarkdown` removes code fences, inline code, images, links (kept text), headings, blockquotes, list markers, HTML tags, and emphasis (bold/italic). Hand-rolled emphasis stripping with separate non-backref patterns per marker form because Go's RE2 doesn't support backreferences. Not a full markdown parser — covers the cases that affect ranking and snippet quality. `tokenize` splits on Unicode-aware non-alphanumeric boundaries (`[^\p{L}\p{N}]+`) so "BSC-123" → `["bsc", "123"]`. `extractSnippet` returns a `~maxLen`-char window centered on the first match with ellipses on truncation.
- MCP tool: `favro_search_cards`. Inputs: `query` (required), exactly one of `widget_common_id` / `collection_id` (Favro's `/cards` endpoint rejects unfiltered listings with HTTP 400; the tool short-circuits with a typed error if neither — or both — are set, guiding the LLM to call `favro_resolve_widget` or `favro_resolve_collection` first). Optional `include_archived` (default false), `limit` (default 10, max 50), `min_score` (drops candidates below the threshold pre-cap), `force_refresh`. Output: ranked `SearchedCard` hits + `cached: bool`. `column_name` is deliberately omitted from each hit — resolving columns per-result would burn the rate-limit budget the cache exists to protect; chain to `favro_get_card_full` for per-card metadata.
- `internal/favro`: added `Card.CustomFieldsValues []CardCustomFieldValue` (was deliberately deferred in Phase 3.6). Each entry carries `CustomFieldID`, raw `Value` (`json.RawMessage` so callers don't have to commit to a Go type for the heterogeneous Favro shapes), `CustomFieldItemIDs` (single/multi-select option references), and `Total` (Rating-style fields). Regression test pins decode for text / number / bool / date / select / multi-select / rating shapes.
- `internal/server`: `Resolver.GetFullCard(ctx, FullCardIdentity, includeComments, commentLimit)` composes resolver caches (tags, users, widgets, columns, collections, custom fields) plus an optional first-page comments fetch to dereference one card's id fields into human-readable names. Identity flavors: `card_id` (per-widget GET /cards/{id}), `card_common_id` (list /cards with `cardCommonId` filter, `unique=true`), `sequential_id` (list /cards with `cardSequentialId` filter, `unique=true`). Exactly one identity required; typed errors `errFullCardIdentityRequired` and `errFullCardNotFound` cover the two failure modes. Custom-field value dereferencing handles the Phase 4.4-scope simple types (Text, Number, Date, Date created, Checkbox, Link, Single select, Multiple select); long-tail types (Members, Status, Rating, Timeline, Voting, Progress, Relations, Sequential ID, Tags) pass through with `dereferenced: false` and the raw JSON attached — Phase 7 fills these in. Sequential fan-out (rather than concurrent) because every dereference hits the warm resolver cache; cold cost is at most 7 round-trips, comfortably within the rate-limit budget.
- MCP tool: `favro_get_card_full`. Inputs: exactly one of `card_id` / `card_common_id` / `sequential_id`, plus optional `include_comments` (default false) and `comment_limit` (default 20). Output: full `FullCard` with every id field dereferenced.

### Added (Phase 5.1 — Write CRUD foundation + favro_create_tag)
- `internal/favro`: `(*Client).PostJSON / PutJSON / PatchJSON / DeleteJSON` wrap `Do` for the four mutating HTTP methods, mirroring the `GetJSON` shape (request + response decoding + dry-run propagation). Each returns `*DryRunRecord` wrapped in `ErrDryRun` when the per-context `WithDryRun` or process-wide `ForceDryRun` gate is set, without touching the network. `doJSON` unifies all five helpers (incl. existing `GetJSON`) so adding new HTTP methods is a one-line dispatch.
- `internal/favro`: regression test `TestDryRun_WriteHelpers_NoRoundTrip` injects an `http.RoundTripper` that fails the test on entry and drives every mutating helper through dry-run mode; pins the contract that dry-run never dispatches a request. Companion `TestDryRun_ForceDryRunOnClient_NoRoundTrip` covers the process-wide gate. The strict round-tripper test catches future regressions a counter-based test could miss.
- `internal/favro`: `Client.CreateTag(ctx, CreateTagRequest{Name, Color})` returns the created `Tag`. `name` is required; `color` is optional (Favro picks randomly when omitted, per docs). Honors per-context `WithDryRun` and process-wide `ForceDryRun`.
- `internal/server`: shared mutation surface — `dryRunInput {DryRun bool}` (embed in any mutation tool's input), `writeOutput[T] {DryRun, Result, WouldCall, RequestBody, PredictedStateDiff}` (the unified output shape), `DryRunCall {Method, URL}`, `mutating(title, destructive)` annotation helper, and `runWrite[T]` which executes a favro write and projects the result into the unified shape. `RequestBody` is `any` (decoded JSON) so the LLM gets a structured object rather than opaque bytes.
- MCP tool: `favro_create_tag`. Inputs: `name` (required), `color` (optional palette name), `dry_run`. Output: `writeOutput[favro.Tag]`. On a successful live write the resolver's tag cache is invalidated (so the next `favro_resolve_tag` / `favro_list_tags` re-fetches and sees the new tag). Dry-run intentionally skips invalidation since no state changed.
- `internal/favro`: added `deleteByID(ctx, basePath, id)` helper to `resources.go` mirroring the existing `getByID` shape — short-circuits with `errMissingID` on empty id, surfaces `*NotFoundError` on 404, propagates the dry-run gate via `DeleteJSON`. `Client.DeleteTag(ctx, tagID)` is the first caller; future `DeleteCard` / `DeleteCollection` / `DeleteWidget` etc. will reuse the helper.
- MCP tool: `favro_delete_tag`. Inputs: `tag_id` (required), `dry_run`. Output: `writeOutput[struct{}]` (delete returns no payload). Annotation: `mutating(_, true)` — destructive, so MCP hosts may warn before auto-confirm. On a successful live delete the resolver's tag cache is invalidated. Dry-run skips invalidation.

### Added (Phase 5.4 — Collections + widgets + columns write CRUD)
- `internal/favro`: `Client.CreateCollection / UpdateCollection / DeleteCollection` over POST/PUT/DELETE `/collections[/{id}]`. `CreateCollectionRequest{Name, Color, Background, IconName, PublicSharing, FullMembersCanAddWidgets, SharedToUsers}`; `UpdateCollectionRequest` mirrors with all fields optional plus `Archive *bool` (so `&false` unarchive isn't omitempty-elided). Empty name on create / empty id on update / delete short-circuit before any HTTP call.
- `internal/favro`: `Client.CreateWidget / UpdateWidget / DeleteWidget` over POST/PUT/DELETE `/widgets[/{id}]`. `CreateWidgetRequest{CollectionID, Name, Type, Color, BreakdownCardCommonID, OwnerRole, EditRole}`; `UpdateWidgetRequest` mirrors plus `Archive *bool`. CollectionID + Name required on create; widgetCommonID required on update / delete.
- `internal/favro`: `Client.CreateColumn / UpdateColumn / DeleteColumn` over POST/PUT/DELETE `/columns[/{id}]`. `CreateColumnRequest{WidgetCommonID, Name, Color, Position *int}` and `UpdateColumnRequest{Name, Color, Position *int}`. `Position` is `*int` so an explicit 0 (top of the column ordering) survives JSON marshalling. WidgetCommonID + Name required on create; columnID required on update / delete. Documented Favro's behavior of rejecting `DELETE /columns/{id}` when the column still contains cards (HTTP 400 — callers must move/archive cards first; the helper does NOT cascade).
- MCP tools: `favro_create_collection`, `favro_update_collection`, `favro_delete_collection`, `favro_create_widget`, `favro_update_widget`, `favro_delete_widget`, `favro_create_column`, `favro_update_column`, `favro_delete_column`. All nine follow the Phase 5.1–5.3 pattern: `dry_run` opt-in, `writeOutput[T]` shape, state-diff describing the would-be change. Annotations: `mutating(_, false)` for create / update; `mutating(_, true)` for the three delete tools.
- `internal/server`: cache invalidation per resource on successful live writes:
  - Collection writes invalidate `collectionCache`. Collection delete additionally invalidates `widgetCache` (Favro doesn't auto-cascade widgets but they may now be unmoored) and the search-cards cache (cards on those widgets may behave differently downstream).
  - Widget writes invalidate `widgetCache`. Widget delete additionally invalidates the column cache (prefix-sweep via new `invalidateAllColumnCaches()`) and the search-cards cache.
  - Column writes invalidate the per-widget column cache when the caller passes `widget_common_id`; otherwise the prefix-sweep fallback drops every cached column list. Defensive default — column write tools can't always discover the parent widget without an extra fetch, so the prefix sweep is the safe fallback (cheap to re-warm lazily).
- `internal/server`: new `Resolver.invalidateAllColumnCaches()` does the `columnCache.InvalidatePrefix(columnCacheKeyPrefix)` sweep — used by widget delete and by column write tools that don't have the parent widget id.

### Fixed (Phase 5.4)
- `internal/favro`: `SharedUser` gained an `Email string \`json:"email,omitempty"\`` field, and `UserID` is now `omitempty`. Favro's collection-create and collection-update bodies accept either `email` or `userId` to identify a user; the previous shape (`UserID` non-omitempty, no `Email`) couldn't express the email path and would have sent `{"userId":"","role":"..."}` for callers passing only an email — Favro 400s that. Read paths still decode existing responses cleanly (Favro returns `userId` on read, never `email`).

### Wire-contract observations from Phase 5.4 live test
- `Collection.publicSharing` accepts at least `"users"` in addition to the `"off"` / `"organization"` / `"public"` values the docs imply (a freshly-created collection came back with `publicSharing: "users"`). The field is already typed as a plain string for exactly this reason; no code change needed.
- `Collection.color` requested as `slategray` came back empty in the response, with `background: "purple"` set instead. Favro appears to silently swap the requested `color` for an auto-assigned `background` on collections — the `color` field may be tag-only despite what the docs hint. Both fields stay on the read type for forward compatibility; tool description preserved.
- `Column` write responses do not echo a `color` field even when one was sent at create time — the standalone `Column` type has no `Color` field (the embedded `Widget.Columns` summary does). Color survives on the wire but isn't surfaced back to the LLM after a column write. Not blocking; future widening can add it if a use case appears.
- Re-deleting a collection / column returns Favro's 403 disambiguator (deleted-or-no-permission, the Phase 4.5 `ForbiddenError`); re-deleting a widget returns 404 (`NotFoundError`). Both are surfaced cleanly through the existing typed-error infrastructure.

### Added (Phase 5.3 — Cards write CRUD)
- `internal/favro`: `Client.CreateCard(ctx, CreateCardRequest)` wraps `POST /cards`. Body fields: `name` (required), `widgetCommonId` (omit to land on the authenticated user's todo list), `columnId`, `laneId`, `parentCardId`, `detailedDescription`, `listPosition` / `sheetPosition` (JSON numbers — see "wire-contract gotchas" below), `assignmentIds`, `tags` (by name — favro layer accepts the auto-create form for completeness; the MCP tool deliberately doesn't expose it), `tagIds`, `startDate`, `dueDate`. Empty name short-circuits with a typed error.
- `internal/favro`: `Client.UpdateCard(ctx, cardID, UpdateCardRequest)` wraps `PUT /cards/{cardId}`. Kitchen-sink body — every field optional. Pointer types appear where "absent" must differ from "zero": `Archive *bool` (nil = don't touch, `&true` archive, `&false` unarchive), `CompleteAssignments *bool`. Tag mutations come in two flavors at the favro layer (`AddTags` / `RemoveTags` by name, `AddTagIDs` / `RemoveTagIDs` by id); the MCP tool surfaces only the `*_tag_ids` flavors. Tasklists, custom fields, and attachment removal are deferred to Phases 5.5 / 7.
- `internal/favro`: `Client.ArchiveCard(ctx, cardID)` and `Client.UnarchiveCard(ctx, cardID)` are thin `UpdateCard` wrappers that send `{archive:true}` / `{archive:false}` explicitly. Pointer-typed `Archive` so `&false` survives JSON marshalling (a plain `bool` would omitempty-elide and silently no-op).
- `internal/favro`: `Client.MoveCard(ctx, cardID, MoveCardRequest{WidgetCommonID, ColumnID, LaneID, DragMode})` is an `UpdateCard` wrapper for the common "move card to <board>" workflow. At least one of widget/column/lane must be set — a fully-empty move short-circuits with a typed error so a silent no-op can't mask a caller bug.
- `internal/favro`: `Client.DeleteCard(ctx, cardID, everywhere bool)` returns `DeleteCardResponse` (a `[]string` named type) — the array of cardIds Favro removed. With `everywhere=false` (default) only the per-widget instance is deleted; with `everywhere=true` the cardCommonId is purged across every widget. Empty cardID short-circuits with `errMissingID`. Implementation calls the package-internal `doJSON` directly (rather than `DeleteJSON`) so the `?everywhere=true` query parameter rides along — `DeleteJSON`'s public signature doesn't accept query.
- MCP tools: `favro_create_card`, `favro_update_card`, `favro_archive_card`, `favro_unarchive_card`, `favro_move_card`, `favro_delete_card`. All six follow the Phase 5.1/5.2 pattern: `dry_run` opt-in, `writeOutput[T]` shape, state-diff describing the would-be change. Annotations: `mutating(_, false)` for everything except `favro_delete_card`, which is `mutating(_, true)` so MCP hosts can warn before auto-confirming destructive ops. Successful live writes invalidate the search-cards cache (`r.invalidateSearchCardCache()`); dry-runs skip the invalidation (no state changed). Live cache-invalidation regression test for `favro_create_card` mirrors the Phase 5.1 pattern. The `favro_move_card` empty-move guard surfaces the favro-layer typed error as a tool error.
- `internal/server`: `updateCardStateDiff` is driven by a small `field {when bool, desc func() string}` dispatch table — `desc` is a closure so each entry's value is computed lazily and pointer derefs (e.g. `*ListPosition`) only fire under their `when` guard.

### Wire-contract gotchas caught live in Phase 5.3
- `listPosition` / `sheetPosition` must be **JSON numbers**, not strings. String values — even numeric ones like `"3.125"` or `"top"` — return HTTP 400 `"Unexpected value of listPosition (optional)"`. `CreateCardRequest`, `UpdateCardRequest`, and `MoveCardRequest` use `*float64` so `0` (top of column) is distinguishable from "absent". The MCP `list_position` / `sheet_position` inputs are typed accordingly.
- A column move (`columnId` set) that **omits `listPosition`** silently no-ops — Favro returns HTTP 200 with an empty body and the card stays put. The `favro_move_card` tool description and `MoveCardRequest` doc both call this out.
- `DELETE /cards/{id}` returns a **bare JSON array** of removed cardIds (e.g. `["ci-1"]`), NOT the `{"cardIds":[...]}` object the docs hint at. `DeleteCardResponse` is a `[]string` named type; favro-layer + MCP-layer test fixtures pin the bare-array shape so a future docs-driven refactor doesn't silently break decode.

### Fixed
- `internal/favro`: changed `Card.Position` / `Card.ListPosition` from `int` to `float64`. Favro uses fractional positions (e.g. `3.125`) so it can slot a card between two siblings without renumbering everything around it; the previous `int` typing 400'd the JSON decode on any non-integer position. Caught live during Phase 4.3 search testing — `favro_list_cards` would have hit the same issue, but the existing tests happened to use only integer positions.
- `internal/favro`: split HTTP 403 out of `AuthError` into a new typed `ForbiddenError` (`Status`, `Path`). Previously both 401 and 403 mapped to `AuthError`, surfacing as `"Favro authentication failed — check FAVRO_USER_EMAIL and FAVRO_API_TOKEN"` even when the credentials were fine and the resource was simply not visible to the token (Favro returns 403 instead of 404 for permission-restricted or non-existent resources, intentionally avoiding existence leakage). The new `ForbiddenError` says `"Favro denied access at <path> (HTTP 403): the resource may not exist or the token lacks permission for it"` and is documented to be functionally equivalent to a not-found from the caller's perspective. Phase 4 workflow tools (search → fetch chains) would have amplified the misleading auth message into LLM dead-ends. `internal/auth/validate.go`'s startup credential check still maps 401||403 to auth-failed because at boot the broadest possible scope (`/organizations`) is unambiguously authentication.

### Changed
- CI: removed the `test-integration` job. It was gated to push-to-main / `integration-ok`-labeled PRs and ran zero tests anyway (no `*_integration_test.go` fixtures exist), so it was cruft. Wire-format coverage is currently done via the maintainer's pre-commit live MCP test; a recorded-fixture replay path can revive a real CI integration job later without ever calling Favro from CI. Repo secrets `FAVRO_USER_EMAIL` / `FAVRO_API_TOKEN` / `FAVRO_ORGANIZATION_ID` referenced by the removed job are no longer used in CI; rotate or delete them in GitHub Settings if you want.
