## [Unreleased]

### Security (Phase 9.1)
- `go.mod`: bump `toolchain` from `go1.26.2` to `go1.26.3` to pick up the stdlib fixes for [GO-2026-4971](https://pkg.go.dev/vuln/GO-2026-4971) (panic in `net.Dial` / `net.LookupPort` on Windows when handling NUL bytes — reachable through `auth.KeyringSource.Delete` and `auth.Validator.Validate`) and [GO-2026-4918](https://pkg.go.dev/vuln/GO-2026-4918) (infinite loop in HTTP/2 transport on a malformed `SETTINGS_MAX_FRAME_SIZE` — reachable through `auth.Validator.Validate`'s startup ping). All CI workflows resolve via `go-version-file: go.mod`, so the toolchain bump in `go.mod` is the only change needed. `govulncheck ./...` reports clean against 1.26.3.

### Added (Phase 9.1 — Broader markdown corpus)
- `internal/server/testdata/markdown/`: 6 new fixtures exercising markdown shapes Phase 6 didn't cover. `nested_lists.md` walks bullet + numbered lists 2 levels deep with `find this` mid-list-item; `blockquotes.md` covers single-level + `> >` nested quotes; `code_fence_with_backticks.md` puts a triple-backtick block inside a four-backtick outer fence (the Markdown-Extra "fence inside a fence" idiom); `unicode_emoji.md` exercises non-ASCII (`é`, `中文`, emoji, leading LRM) so the byte-level prefix/suffix invariants in `appendDescription` / `prependDescription` are confirmed against multi-byte runes; `task_list.md` covers GitHub-style `- [x]` / `- [ ]` checkboxes; `html_inline.md` covers `<details>`, `<sub>`, and inline `<br/>` mixed with prose. `TestDescriptionEditors_GoldenCorpus` walks the directory so each new file auto-joins the regression set without test changes — adds 18 new sub-tests (6 × append/prepend/replace).

## [1.0.0] — 2026-05-07

First stable release. The Phase 0 → 8 build sequence is complete: full CRUD coverage of every Favro REST resource (collections, widgets, columns, cards, comments, tags, custom fields, groups, organizations, users), workflow tools for natural-language use (search, name resolution, surgical description edits, comment-by-card-name, tag-by-name), dry-run on every mutating tool, and a single multi-arch `favro-mcp.plugin` zip that registers the binary as an MCP server in a Claude Code or Cowork profile. 64 MCP tools registered.

### Changed (Phase 8.3 — README + docs polish for v1.0)
- `README.md`: rewritten for v1.0 readiness. New **Installation** section covers three install paths (Cowork plugin from GitHub Release as recommended, standalone binary download, build from source) — replaces the bare `make build` + `Running locally` snippets. **Authentication** expanded with the full `auth` subcommand walkthrough (`login`/`status`/`logout`/`which`), explicit credential-resolution order, and a separate **MCP host configuration** subsection that covers both the keyring path (zero secrets in config) and the headless / CI env-var variant. New **Dry-run** section documents the per-tool `dry_run: true` parameter and the process-wide `--dry-run` binary flag. New **Troubleshooting** table covers the most common failure modes: missing credentials, missing `FAVRO_ORGANIZATION_ID`, HTTP 429 with `Retry-After`, paginated-read pitfalls, the SPA-fallback HTML response Favro returns for non-endpoints (with the `decodeJSONLenient` diagnostic shape), cache-invalidation `force_refresh` escape hatch, and the Windows / Linux non-bash launcher fallback (point `.mcp.json` directly at `bin/<os>-<arch>/favro-mcp[.exe]`). **Status** line updated from "Phase 3" to current — points at CHANGELOG and v1.0. The "tool index will land at v1.0" stub line removed; the table already documents all 64 registered tools.

### Added (Phase 8.2 — Cowork plugin packaging)
- `plugin-template/`: source-of-truth manifest + `.mcp.json` for the Cowork plugin bundle. `plugin-template/.claude-plugin/plugin.json` carries the `0.0.0-placeholder` sentinel that the package script substitutes from goreleaser metadata at packaging time so the manifest version always matches the build artifact. `plugin-template/.mcp.json` uses `${CLAUDE_PLUGIN_ROOT}/bin/favro-mcp` so the plugin is relocatable across hosts (distinct from any local-dev `.mcp.json` at the repo root, which points at a workstation-specific build path).
- `scripts/package-plugin.sh`: builds the multi-arch `favro-mcp.plugin` zip from goreleaser's `dist/`. Reads binary paths from `dist/artifacts.json` via `jq` so the script doesn't duplicate goreleaser's path-template knowledge (no `_v1` / `_v8.0` suffix glob fragility); reads version from `dist/metadata.json`. Stages binaries into `bin/<goos>-<goarch>/`, generates a bash launcher shim at `bin/favro-mcp` that picks the right arch via `uname -s -m`, bundles LICENSE + NOTICE + README.md, then zips with deterministic file ordering (LC_ALL=C sorted) for byte-identical output across re-runs. Windows path is best-effort for v1.0: the launcher errors out on Windows with a message pointing at `bin/windows-amd64/favro-mcp.exe` for direct invocation.
- `Makefile`: new `make package-plugin` target runs a goreleaser snapshot then the package script — local dev parity with the release pipeline.
- `.github/workflows/release.yml`: plugin packaging folded into the existing `goreleaser` job (separate-job split lost `dist/` between runners). Adds two steps after `goreleaser release --clean`: `scripts/package-plugin.sh` and `gh release upload "${{ github.ref_name }}" favro-mcp.plugin --clobber`. Both gated by `if: ${{ !contains(github.ref, '-') }}` so pre-release tags ship binaries but no `.plugin` (plugins represent stable installs). Removes the now-dead separate `package-plugin` job; `goreleaser` job's pre-Phase-8 shell guard is gone since `.goreleaser.yaml` shipped in 8.1.

### Added (Phase 7.2 — Bulk tag updates as client-side fan-out)
- `internal/favro`: `Client.UpdateTags(ctx, []BulkTagUpdate)` applies multiple tag updates concurrently. Plan deviation, caught live: Favro has NO real bulk-tag endpoint — `PUT /tags` (no `tagId`) returns the SPA fallback HTML page (status 200, content-type `text/html`, body `<p>It looks like you don't have any client routes defined…</p>`). The plan note "Favro's `PUT /tags` is the only bulk-write endpoint" was wrong; documented surface only includes the per-tag `PUT /tags/{tagId}` already shipped in Phase 5.2. Pivoted to a client-side parallel fan-out: the bulk method dispatches one `PUT /tags/{tagId}` per entry via `errgroup.WithContext` with `SetLimit(updateTagsConcurrency = 4)` so a wide bulk doesn't burn the rate-limit budget all at once. Returned `[]Tag` is in input order; on the first per-entry error errgroup cancels remaining in-flight work and the wrapped error names both the offending tagId and its input index so callers can recover from partial successes. Dry-run synthesizes a single conceptual `*DryRunRecord` (Method=PUT, URL `…/tags/{tagId} × N (client-side parallel fan-out)`, Body the input array) and returns it wrapped in `ErrDryRun` without dispatching any HTTP work.
- MCP tool: `favro_update_tags`. Inputs: `updates` (required array of `{tag_id, name?, color?}`), `dry_run`. Output: `writeOutput[[]favro.Tag]`. Tool description loudly surfaces the fan-out reality so the LLM doesn't assume one-round-trip semantics. Successful live writes invalidate the org-global tag cache so the next `favro_resolve_tag` / `favro_list_tags` re-fetches; dry-run intentionally skips invalidation. State-diff lists each entry's per-field changes (`tag "id": name → "x", color → "y"`) and reports per-entry no-ops so a fully no-op bulk request is visible to the LLM before sending.

### Wire-contract observations from Phase 7.2 live test
- `PUT /tags` (no `tagId`) is **not** a real Favro API endpoint. Status 200 + `text/html` body `<p>It looks like you don't have any client routes defined…</p>` is the SPA fallback page returned for unmatched routes. The plan claim that "Favro's `PUT /tags` is the only bulk-write endpoint" was incorrect; pivoted to client-side parallel fan-out (see above).
- `internal/favro`: enriched `decodeJSONLenient` to include `status`, `content-type`, and a 256-char body-prefix in the decode-error message. The original "favro: decode response from /api/v1/tags: invalid character '<' looking for beginning of value" error didn't surface enough to diagnose the wire-contract gap; the new shape ("status=200, content-type=\"text/html\", body-prefix=\"<p>It looks like…\"") would have made it obvious in one round-trip. Kept regardless of the Phase 7.2 pivot — this is real diagnostic improvement for any future wire-contract investigation. Switched the implementation from streaming `json.Decoder.Decode(out)` to `io.ReadAll` + `json.Unmarshal` so the body is available for both decode and error paths; trailing-token detection preserved.

### Added (Phase 7.1 — Attachments)
- `internal/favro`: `Client.UploadAttachment(ctx, cardID, filename, content)` posts raw bytes to `POST /cards/{cardId}/attachment?filename=…` with `Content-Type: application/octet-stream`. Returns `CardAttachment` (`{Name, FileURL}`) — verified live that Favro echoes the *attachment object*, NOT the updated Card the docs hint at. Empty `cardID` short-circuits with `errMissingID`; empty `filename` with new `errMissingFilename`. An 8 MiB cap (`UploadAttachmentMaxBytes`) is enforced before any HTTP work — Favro's documented limit is 10 MiB; the cap leaves headroom for HTTP framing and concurrent in-flight bodies.
- `internal/favro`: extended `UpdateCardRequest` with `RemoveAttachments []string` (the field was deferred from Phase 5.3). `Client.RemoveAttachment` is also added but is **NOT exposed at the MCP layer** — see "Wire-contract observations" below.
- `internal/favro`: fixed `buildRequest` and `buildDryRunRecord` so a caller-supplied `Content-Type` via `WithHeader` fully overrides the JSON default. The previous `req.Header.Add(k, v)` pattern produced a comma-joined `application/json, application/octet-stream` pair on binary uploads, which Favro rejects. Caller-supplied `Content-Type` now uses `Header.Set`; the JSON default is only applied when `extra.Get("Content-Type")` is empty. Pinned by `TestBuildRequest_ContentTypeOverride`.
- `internal/favro`: extracted the JSON-decode-with-EOF-tolerance logic from `doJSON` into a reusable `decodeJSONLenient` helper so `UploadAttachment`'s non-doJSON code path (raw-bytes request, JSON response) shares the same decode semantics.
- MCP tool: `favro_upload_attachment` (reads from a local `file_path`; defaults `filename` to the file's basename; rejects non-regular files and oversize blobs locally before any HTTP work). Successful live writes invalidate the search-cards cache (cached card payloads carry stale attachment lists otherwise).

### Wire-contract observations from Phase 7.1 live test
- `POST /cards/{cardId}/attachment` returns the **attachment object** `{name, fileURL}`, NOT the updated Card the docs hint at. Decoding into Card silently fills only `Name` and leaves the rest zero — masking the contract. `UploadAttachment` now decodes into `CardAttachment` directly; tests pin the bare-object shape.
- `PUT /cards/{cardId}` with `removeAttachments: ["filename"]` is **silently no-op'd** by Favro — verified live with both the display name and the underlying S3 object name. Favro returns 200 but the attachment stays on the card. `Client.RemoveAttachment` is kept as code (with the `RemoveAttachments` field on `UpdateCardRequest`) for a future investigation, but the `favro_remove_attachment` MCP tool is intentionally NOT registered until the right wire shape is found.

### Added (Phase 6 — NL workflow write layer)
- `internal/favro`: `Client.GetCardWithDescriptionFormat(ctx, cardID, format)` is the single-card read variant Phase 6's editor tools rely on — Favro defaults to plaintext, but the surgical-edit path needs the body returned in markdown so the round-trip stays edit-correct. Empty cardID short-circuits with `errMissingID`; empty format falls through to Favro's default.
- `internal/server`: `description.go` carries the editor algorithms: `appendDescription` / `prependDescription` (with `\n\n` separator, dropped when the existing body is empty so a fresh card doesn't lead with a stray paragraph); `replaceInDescription` (literal or regex with `$N` backrefs); `unifiedDiff` via `pmezard/go-difflib`; `editorResult{Old, New, UnifiedDiff}` is the per-tool result shape.
- MCP tools: `favro_append_card_description`, `favro_prepend_card_description`, `favro_replace_in_card_description`. Each reads with `descriptionFormat=markdown`, builds the new body locally, PUTs `detailedDescription`, and returns `{old, new, unified_diff}`. `replace_in_card_description` defaults `count: 1` (typed as `*int` so explicit `0` — replace-all — is distinguishable from JSON-omitted), and refuses to PUT an unchanged body when `find` matched nothing. Live success invalidates the search-cards cache. The dry-run path always populates `Result` (the diff IS the value — dry-run without the diff would force the LLM to compute it itself or PUT to find out), deviating from the standard `runWrite` pattern.
- MCP tool: `favro_add_comment_to_card`. Accepts one of `card_common_id` / `card_id` / `sequential_id` (the integer of a 'BSC-123' ref) / `search_query`. With `search_query` the tool runs `favro_search_cards` with `limit=2` in the supplied `widget_common_id` or `collection_id` scope; if the top-2 scores are within `0.2` it returns `{ambiguous: true, candidates: [...]}` without posting, so the LLM picks one and re-runs with the explicit `card_common_id`. `card_id` and `sequential_id` are resolved to a `cardCommonId` via the existing `fetchCardForIdentity` helper before the post.
- MCP tools: `favro_add_tag_to_card` / `favro_remove_tag_from_card`. By tag NAME — hard-fails on unknown names with an error pointing at `favro_create_tag` (typo prevention is the whole point). Multiple tags sharing the exact name (Favro doesn't enforce uniqueness) surfaces as a typed error suggesting the LLM use `favro_update_card` with explicit `add_tag_ids` / `remove_tag_ids`. Live success invalidates the search-cards cache.
- `internal/server/testdata/markdown/`: 4-fixture corpus (code fences, lists / headings, table, empty body) plus `TestDescriptionEditors_GoldenCorpus` regressions exercising each editor against each shape — pinning that append keeps the original body as a prefix, prepend keeps it as a suffix, and replace only modifies the matching region.
- Promoted `github.com/pmezard/go-difflib` from indirect (transitive via `testify`) to a direct require so the dependency is explicit.

### Added (Phase 4 — NL workflow read layer)
- `internal/server`: `Resolver` struct holds a `*favro.Client` plus seven per-resource `cache.TTL[…]` caches (tags, users, collections, widgets, columns, custom fields, groups). Constructed once per `mcp.Server` so cache state is process-wide. Cache TTLs follow plan §7 (5 minutes for slow-changing org metadata: tags, users, custom fields, groups; 60 seconds for collection-scoped lists: collections, widgets, columns).
- `internal/server`: generic `listAllCached[T]` helper centralises the cache-lookup + paginated fetch + cache-write protocol so each resolver method is a 3-line delegation. Reuses `favro.Paginate` for the page walk.
- `internal/server`: `Resolver.Resolve{Tag,User,Collection,Widget,Column,CustomField,Group}(ctx, name, ..., limit, forceRefresh)` return ranked candidates. Score scale: exact match 1.0, prefix 0.7, substring 0.4, no match filtered. Tie-break by name ascending so ordering is deterministic. `limit <= 0` defaults to 10; `limit > 50` is capped at 50 per plan §6a.
- `internal/server`: `Resolver.ResolveUser` matches against the **better of name and email** so an LLM asking for "alice" or "alice@example" both work; email is included in `ResolvedUser` for disambiguation.
- `internal/server`: `Resolver.ResolveWidget` accepts an optional `collectionID` filter applied client-side (avoids a per-collection cache key with redundant data); `ResolvedWidget` includes `Type` and `CollectionIDs` so multiple "Sprint Board" widgets in different collections are distinguishable.
- `internal/server`: `Resolver.ResolveColumn` requires `widgetCommonID` — column names ("Doing", "Done") repeat across widgets and an unscoped resolver would always return ambiguous garbage. Returns `errMissingResolveWidgetCommonID` (typed sentinel) on empty input. Cache is keyed per-widget.
- `internal/server`: `Resolver.ResolveCustomField` includes the field `Type` ("Single select", "Date", etc.) in `ResolvedCustomField` so an LLM can disambiguate between multiple "Priority" fields of different kinds.
- `internal/server`: per-resource `invalidate{Tag,User,Collection,Widget,Column,CustomField,Group}Cache()` package-private hooks for Phase 6 mutating tools to call after successful create / update / delete.
- MCP tools: `favro_resolve_{tag,user,collection,widget,column,custom_field,group}`. All return a candidate list (possibly empty) plus a `cached: bool` so callers know whether a `force_refresh` follow-up might surface newly-created items. `favro_resolve_column` requires `widget_common_id` at the JSON-schema layer (mirrors the underlying API constraint).
- `internal/server`: `Resolver.SearchCards(ctx, query, scope, scopeID, includeArchived, limit, minScore, forceRefresh)` runs a local full-text search over the cards in scope and returns ranked `SearchedCard` hits with snippet, since Favro has no native FT search. Score components are additive (max ~2.0): name phrase +1.0, name token overlap up to +0.6, body phrase +0.5, body token overlap up to +0.5. Distinct-token hits (a token appearing twice still counts once) so the ranker doesn't bias toward verbose cards. Tie-break by name ascending. Empty query short-circuits to no results without touching Favro.
- `internal/server`: `searchCardCache cache.TTL[scopedCorpus]` on Resolver, where `scopedCorpus` holds the raw card list plus its pre-stripped + pre-lowercased name and body strings as parallel slices. Pre-processing once at fetch time means warm-cache repeat queries against the same scope skip both the markdown sweep (~14 regex passes per card) and the per-card `strings.ToLower` (otherwise run by ranker + snippet ≈ 3× per card per query). Cache key format `search:widget:<id>[:+archived]` / `search:collection:<id>[:+archived]` so a single `InvalidatePrefix("search:")` (via `invalidateSearchCardCache`) drops every variant. Plan §7's 60-second TTL. Both scopes paginate fully — the scope's natural size bounds the cost. Every fetch sets `descriptionFormat=markdown` so the markdown stripper sees the format it expects.
- `internal/server`: `stripMarkdown` removes code fences, inline code, images, links (kept text), headings, blockquotes, list markers, HTML tags, and emphasis (bold/italic). Hand-rolled emphasis stripping with separate non-backref patterns per marker form because Go's RE2 doesn't support backreferences. Not a full markdown parser — covers the cases that affect ranking and snippet quality. `tokenize` splits on Unicode-aware non-alphanumeric boundaries (`[^\p{L}\p{N}]+`) so "BSC-123" → `["bsc", "123"]`. `extractSnippet` returns a `~maxLen`-char window centered on the first match with ellipses on truncation.
- MCP tool: `favro_search_cards`. Inputs: `query` (required), exactly one of `widget_common_id` / `collection_id` (Favro's `/cards` endpoint rejects unfiltered listings with HTTP 400; the tool short-circuits with a typed error if neither — or both — are set, guiding the LLM to call `favro_resolve_widget` or `favro_resolve_collection` first). Optional `include_archived` (default false), `limit` (default 10, max 50), `min_score` (drops candidates below the threshold pre-cap), `force_refresh`. Output: ranked `SearchedCard` hits + `cached: bool`. `column_name` is deliberately omitted from each hit — resolving columns per-result would burn the rate-limit budget the cache exists to protect; chain to `favro_get_card_full` for per-card metadata.
- `internal/favro`: added `Card.CustomFieldsValues []CardCustomFieldValue` (was deliberately deferred in Phase 3.6). Each entry carries `CustomFieldID`, raw `Value` (`json.RawMessage` so callers don't have to commit to a Go type for the heterogeneous Favro shapes), `CustomFieldItemIDs` (single/multi-select option references), and `Total` (Rating-style fields). Regression test pins decode for text / number / bool / date / select / multi-select / rating shapes.
- `internal/server`: `Resolver.GetFullCard(ctx, FullCardIdentity, includeComments, commentLimit)` composes resolver caches (tags, users, widgets, columns, collections, custom fields) plus an optional first-page comments fetch to dereference one card's id fields into human-readable names. Identity flavors: `card_id` (per-widget GET /cards/{id}), `card_common_id` (list /cards with `cardCommonId` filter, `unique=true`), `sequential_id` (list /cards with `cardSequentialId` filter, `unique=true`). Exactly one identity required; typed errors `errFullCardIdentityRequired` and `errFullCardNotFound` cover the two failure modes. Custom-field value dereferencing handles the Phase 4.4-scope simple types (Text, Number, Date, Date created, Checkbox, Link, Single select, Multiple select); long-tail types (Members, Status, Rating, Timeline, Voting, Progress, Relations, Sequential ID, Tags) pass through with `dereferenced: false` and the raw JSON attached — Phase 7 fills these in. Sequential fan-out (rather than concurrent) because every dereference hits the warm resolver cache; cold cost is at most 7 round-trips, comfortably within the rate-limit budget.
- MCP tool: `favro_get_card_full`. Inputs: exactly one of `card_id` / `card_common_id` / `sequential_id`, plus optional `include_comments` (default false) and `comment_limit` (default 20). Output: full `FullCard` with every id field dereferenced.

### Added (Phase 5.1 — Write CRUD foundation + favro_create_tag)
- `internal/favro`: `(*Client).PostJSON / PutJSON / PatchJSON / DeleteJSON` wrap `Do` for the four mutating HTTP methods, mirroring the `GetJSON` shape (request + response decoding + dry-run propagation). Each returns `*DryRunRecord` wrapped in `ErrDryRun` when the per-context `WithDryRun` or process-wide `ForceDryRun` gate is set, without touching the network. `doJSON` unifies all five helpers (incl. existing `GetJSON`) so adding new HTTP methods is a one-line dispatch.
- `internal/favro`: regression test `TestDryRun_WriteHelpers_NoRoundTrip` injects an `http.RoundTripper` that fails the test on entry and drives every mutating helper through dry-run mode; pins the contract that dry-run never dispatches a request. Companion `TestDryRun_ForceDryRunOnClient_NoRoundTrip` covers the process-wide gate. The strict round-tripper test catches future regressions a counter-based test could miss.
- `internal/favro`: `Client.CreateTag(ctx, CreateTagRequest{Name, Color})` returns the created `Tag`. `name` is required; `color` is optional (Favro picks randomly when omitted, per docs). Honors per-context `WithDryRun` and process-wide `ForceDryRun`.
- `internal/server`: shared mutation surface — `dryRunInput {DryRun bool}` (embed in any mutation tool's input), `writeOutput[T] {DryRun, Result, WouldCall, RequestBody, PredictedStateDiff}` (the unified output shape), `DryRunCall {Method, URL}`, `mutating(title, destructive)` annotation helper, and `runWrite[T]` which executes a favro write and projects the result into the unified shape. `RequestBody` is `any` (decoded JSON) so the LLM gets a structured object rather than opaque bytes.
- MCP tool: `favro_create_tag`. Inputs: `name` (required), `color` (optional palette name), `dry_run`. Output: `writeOutput[favro.Tag]`. On a successful live write the resolver's tag cache is invalidated (so the next `favro_resolve_tag` / `favro_list_tags` re-fetches and sees the new tag). Dry-run intentionally skips invalidation since no state changed.

### Wire-contract gotchas caught live in Phase 5.3
- `listPosition` / `sheetPosition` must be **JSON numbers**, not strings. String values — even numeric ones like `"3.125"` or `"top"` — return HTTP 400 `"Unexpected value of listPosition (optional)"`. `CreateCardRequest`, `UpdateCardRequest`, and `MoveCardRequest` use `*float64` so `0` (top of column) is distinguishable from "absent". The MCP `list_position` / `sheet_position` inputs are typed accordingly.
- A column move (`columnId` set) that **omits `listPosition`** silently no-ops — Favro returns HTTP 200 with an empty body and the card stays put. The `favro_move_card` tool description and `MoveCardRequest` doc both call this out.
- `DELETE /cards/{id}` returns a **bare JSON array** of removed cardIds (e.g. `["ci-1"]`), NOT the `{"cardIds":[...]}` object the docs hint at. `DeleteCardResponse` is a `[]string` named type; favro-layer + MCP-layer test fixtures pin the bare-array shape so a future docs-driven refactor doesn't silently break decode.

- `internal/favro`: changed `Card.Position` / `Card.ListPosition` from `int` to `float64`.
